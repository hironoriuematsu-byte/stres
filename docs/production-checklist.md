## 1. Supabase を Pro 化する

料金プランは**組織(Organization)単位**です。プロジェクト単位ではありません。

1. https://supabase.com/dashboard → 左上で対象の組織を選択
2. **Organization Settings → Billing → Plan** から Pro にアップグレード
3. **請求先情報(Billing Address / Billing Email)を会社の情報に設定**
   - 会社名: Mestate LLC(うえまつ産業医事務所)
   - 住所: 京都府京都市中京区錦小路通室町西入天神山町280 4階
   - 請求書の宛先メール: 会社のアドレス(例: hironori.uematsu@mestate.jp)
   - 日本の適格請求書(インボイス)登録番号がある場合は Tax ID 欄に登録
4. 支払方法を会社のカードに設定

### Pro 化で得られる主なもの(本運用で重要な順)

| 項目 | Free | Pro |
|---|---|---|
| **プロジェクトの自動停止** | 1週間アクセスがないと**一時停止** | **なし**(常時稼働) |
| **日次バックアップ** | なし | **あり(7日分)** |
| データベース容量 | 500MB | 8GB〜 |
| ログの保持 | 1日 | 7日 |
| サポート | コミュニティ | メール |

- **自動停止がなくなること**が本運用では決定的です(Free のままだと、受検期間が空いた企業でアクセスが途絶えた際にプロジェクトが停止し、受検も結果閲覧もできなくなります)。
- **日次バックアップ**は、5年保存義務のあるデータを扱ううえで必須と考えてください。
- より細かい復元が必要なら PITR(Point in Time Recovery)が有料アドオンとして追加できますが、当面は日次バックアップで十分です。

### 費用の目安

Pro は **$25/月(組織あたり)**。プラン料金は組織に1回だけですが、**$25 に含まれる compute クレジットは $10 分(= 最小インスタンス1つ分)**です。

> **同じ組織に2つ目のプロジェクトがあると、その compute 代 +$10/月 が上乗せ**されます(例: 本番 + 開発用 = $35/月)。
> Pro 組織の中に「無料のプロジェクト」は置けません。無料で使いたいプロジェクトは**別組織(Freeプラン)**に置く必要があります。

→ 最終形(健康管理Webを本番プロジェクトに相乗り = **プロジェクト1つ**)では **$25/月のまま**で、健康管理Webのぶんの追加費用は発生しません。
→ ただし**開発期間中に開発用プロジェクトを別に持つ間は +$10/月**です。詳しくは「11. 開発用プロジェクトの扱い」を参照。

※ 金額は変更される可能性があります。申込画面の表示金額でご確認ください。

## 4. 認証メールを本番仕様にする(重要)

現在、**アカウント登録の確認メール・招待メール・パスワード再設定メールは Supabase の内蔵メール送信**で送られています。内蔵の送信サービスは**開発・検証用**で、送信レートが厳しく制限されています。

> 100名規模の会社で一斉に登録を案内すると、**内蔵メールでは途中から送信されなくなります。**(申出通知メールで以前起きた「実施者にしか届かない」現象と同じ原因の別バージョンです)

### 対応

1. Supabase → **Authentication → Emails → SMTP Settings** で **Custom SMTP を有効化**し、Resend を設定する
   - Host: `smtp.resend.com` / Port: `465`(または 587) / User: `resend` / Password: Resend の API キー
   - Sender: 既に Resend で認証済みの送信元アドレスを使用
2. **Authentication → Rate Limits** の「Emails」上限を、想定する一斉登録の人数以上に引き上げる
3. **Authentication → URL Configuration** の Site URL / Redirect URLs が本番URLになっていることを確認(独自ドメインを設定する場合は手順6のあとに追加)
4. メールテンプレート(Confirm signup / Invite user / Reset password / Change Email Address)の日本語化 ― 未実施であればこの機会に

## 5. Vercel を Pro 化する【実施済み: 2026-09-06】

Vercel の Hobby プランは**個人の非商用利用向け**です。商用利用は Pro が必要になります。

### 実際に行った方法(推奨・チーム作成は不要)

**個人アカウント(スコープ)そのものを Pro にアップグレードできます。**チームを新規作成してプロジェクトを移管する必要はありません。

1. ダッシュボードのアップグレード導線から「Upgrade <アカウント名>'s projects to Pro」のダイアログを開く
2. 支払い方法に**会社のカード**を入力する
   - 個人アカウントのメールに紐づく保存済みカード(Link)が既定で選ばれている場合は、メールアドレス欄の **✕** を押して解除し、会社のカードを直接入力する
3. 「Free domain with Pro $0」は**不要**(独自ドメイン `mestate.jp` を保有しているため)
4. **Upgrade** を押す

**この方法の利点**: `stres.vercel.app` のURL、環境変数、GitHub連携がすべてそのまま維持され、プロジェクトの移管に伴うリスク(URL変更で配布済みQRが無効になる等)が発生しません。

> チームを作成してプロジェクトを移管する方法もありますが、**URLが変わる可能性があるため、この用途では選ぶ理由がありません。**作りかけのチームが残っている場合は、二重課金を避けるため `https://vercel.com/<チーム名>` で存在を確認し、不要なら削除してください。

### Pro 化のあとに行うこと

1. **請求先を会社に設定**: Settings → Billing で会社名(Mestate LLC / うえまつ産業医事務所)、住所、請求書送付先メール、インボイス登録番号(Tax ID)を登録
2. **Deployment Protection を確認**: プロジェクト → Settings → Deployment Protection。**Production に保護がかかっていると受検URLが開けません。**Vercel Authentication は Preview のみ、または無効にする
3. **メンバーは増やさない**: Pro は**メンバー1人あたりの課金**です
4. **アカウント表示名の変更(任意)**: Settings から `Mestate LLC` などに変更可(動作・請求には影響しません)

### 必要な環境変数(移管や再作成をする場合の控え)

| 変数名 | 値の入手先 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 同上(anon public key) |
| `SUPABASE_SERVICE_ROLE_KEY` | 同上(service_role key・**秘密**) |
| `RESEND_API_KEY` | Resend で新規作成(既存キーの値は再表示できない) |
| `SENDER_EMAIL` | 通知メールの差出人アドレス。Resend → Domains で認証済みのもの |

### Pro 化後の確認

- [ ] `https://stres.vercel.app` が**ログインなしで**開く
- [ ] 配布URL(`/join/...`)が開き、新規登録できる

## 6. 独自ドメイン(任意・強く推奨)

`mestate.jp` をお持ちなので、**`stres.mestate.jp`** のようなサブドメインを割り当てられます。

**利点**: 今後 Vercel 側の事情(チーム移管など)でURLが変わっても、**配布済みのQR・URLが生き続けます。**独自ドメインにしておけば、この先の移行でQRを刷り直す必要がなくなります。

### データへの影響: ありません

- **受検データ・アカウントはすべて Supabase(データベース)にあります。**Vercel はプログラムを配信しているだけで、ドメインの追加はデータに一切触れません。
- 独自ドメインは**「追加」であって「置き換え」ではありません。**`stres.vercel.app` も引き続き使えるため、**配布済みのQR・URLはそのまま有効**です。デモページも両方のURLで開けます。
- 両方のURLが**同じアプリ・同じデータベース**を指します。どちらから入っても同じ結果が見えます。
- 唯一の実害は、**新ドメインでは再ログインが必要**になることだけです(ログイン状態はドメインごとに管理されるため)。

> ⚠️ 追加するのは **`stres.mestate.jp`**(サブドメイン)です。`mestate.jp` を入力すると、会社ホームページのアドレスをこのアプリに向ける設定になってしまいます。
> 「Redirect apex domains to www」のチェックは外します(サブドメインには関係しないため)。

手順:

**① Vercel のプロジェクト → Settings → Domains で `stres.mestate.jp` を追加**
   - Connect to an environment → **Production** を選択
   - 追加直後は「Invalid Configuration」と表示される(DNS未設定のため。正常)
   - 画面に **Type / Name / Value** の表が出る。この値をそのままDNSに登録する
   - 例: `CNAME` / `stres` / `cname.vercel-dns.com`(**実際の値は必ず画面の表示に従う**)

**② DNSの管理場所で、その1件を追加する**
   - **種別(Type)**: CNAME
   - **ホスト名(Name / ホスト / 名前)**: `stres` ← 入力欄の右に「.mestate.jp」と表示されるタイプの画面では **`stres` だけ**を入力する。何も補われない画面なら `stres.mestate.jp` と入力
   - **値(Value / 内容 / VALUE)**: Vercelが表示した値(末尾のドットは付けても付けなくてもよい)
   - **TTL**: 既定のまま(3600 / 自動)
   - **既存のレコード(@ / www / MX)は絶対に触らない** ― メールもホームページも影響を受けない
   - Cloudflare をお使いの場合は、そのレコードを **DNS only(グレーの雲)** にする(オレンジの雲=プロキシ有効だと接続できない)
   - サブドメインに CNAME が使えないDNSの場合は、Vercel が代替として表示する **A レコード**を登録する
**③ 反映を待つ**(数分〜長くて数時間)。Vercel の Domains 画面で **Refresh** を押し、**Valid Configuration** になれば完了(SSL証明書は自動で発行される)

**④ Supabase の Authentication → URL Configuration を更新**
   - **Redirect URLs に `https://stres.mestate.jp/**` を追加**する ← 置き換えず、`stres.vercel.app` も残す(両方から登録・パスワード再設定ができるように)
   - Site URL は新ドメインに変更してよい

**⑤ 動作確認** ― 新ドメインでログイン、配布URL・QRの表示、パスワード再設定メールのリンク先

**⑥ 以後は新ドメインで「配布URL・QR」を開き直して配布**(既に配った分もそのまま使えます)

**⑦(任意・後日)** `stres.vercel.app` へのアクセスを新ドメインへ転送したい場合は、Vercel の Domains 設定でリダイレクトを設定できます。パスは維持されるため、**古いQRからでも自動的に新ドメインへ移動**します

### うまくいかないときの確認

| 症状 | 原因と対処 |
|---|---|
| いつまでも Invalid Configuration | DNSの反映待ち(最大数時間)。`stres` の既存レコードが別にないか確認 |
| 「Conflicting record」と出る | 同じホスト名 `stres` に A や CNAME が既にある。古いほうを削除 |
| ページが開かない・証明書エラー | Cloudflare のプロキシ(オレンジの雲)がオンになっていないか確認 |
| 証明書が発行されない | ドメインに CAA レコードがあり Let's Encrypt が許可されていない可能性 |

> 健康管理Web も同様に `kenko.mestate.jp` を割り当てると、2つのシステムを同じドメイン配下で運用できます。

## 11. 開発用プロジェクト(kenko-kanri-dev)の扱い

Pro 化すると、同じ組織にある開発用プロジェクトにも compute 代 **+$10/月** がかかります(Pro 組織の中に無料プロジェクトは置けないため)。選択肢は3つです。

### 案A(推奨): 開発期間中だけ $10 を払い、本番接続後に削除する

- 稼働中のストレスチェックWeb(医療データ・5年保存)に、開発中のSQLを一切当てずに済む
- 健康管理Webの `0101_` 以降のSQLを本番プロジェクトに適用し、動作確認できた時点で **kenko-kanri-dev を削除** → **$25/月に戻る**
- 開発期間を仮に3か月とすれば追加コストは合計 $30 程度。稼働中システムを壊すリスクの保険としては安い

### 案B: 開発用プロジェクトを別の無料組織へ移す

- Supabase で**新しい組織(Freeプラン)を作成**し、`kenko-kanri-dev` をその組織へ Transfer する

- ただし Free プランには**プロジェクト数の上限**があり、また**組織間の移管に条件がある**場合があります。ダッシュボードの Project Settings → Transfer project で可否と条件を確認してください
