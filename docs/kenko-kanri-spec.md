# 健康管理システム(仮称: 健康管理Web)要件定義書

- 発行: うえまつ産業医事務所(Mestate LLC)
- 作成日: 2026-07-30
- 位置づけ: 稼働中の「ストレスチェックWeb」(https://stres.vercel.app)と同じSupabaseプロジェクトに**追加**する形で開発する、産業保健活動の統合管理システムの要件定義書。新規リポジトリ・新規セッションでの開発に引き継ぐことを目的とする。

---

## 1. 目的

産業医業務における各企業(事業場)との情報交換をスムーズにし、社員の健康管理を行いやすくする。具体的には以下を一元管理する:

1. 安全衛生委員会の議事録
2. 健康診断結果(定期健診・雇入時健診等)と事後措置
3. ストレスチェック結果(既存ストレスチェックWebとの連携)
4. 産業医面談の管理(高ストレス面接指導・長時間労働面談・健診事後措置面談・復職面談など)

## 2. 前提: 既存システム(ストレスチェックWeb)の構成

新システムはこの構成を**変更せずに**利用・参照する。

- 技術: Next.js 14 (App Router) + Supabase (Auth / Postgres / RLS) + Vercel、メールはResend(送信ドメイン mestate.jp)
- Supabaseプロジェクト: `mdspuujgiffyvmddtwhn`(共用する)
- 主要テーブル: `companies`(企業)、`profiles`(ユーザー属性: role/氏名/社員番号/部署/誓約)、`results`(ストレスチェック結果、unique(user_id, fiscal_year))、`interview_requests`(面接指導申出)、`access_logs`(監査ログ)、`campaigns`(受検用配布URL)
- ロール(profiles.role): `office`(実施者=産業医事務所・全企業横断)/ `jimu`(実施事務従事者・誓約必須・自社のみ)/ `employee`(従業員・本人分のみ)/ `company`(企業側担当者・**現在未使用**。テーブル制約上は既存)
- 設計原則(新システムでも踏襲する):
  - 行レベルセキュリティ(RLS)+ 列単位GRANTで最小権限
  - 危険・横断的な操作はすべて SECURITY DEFINER のRPC関数(関数内で権限チェック+`access_logs`へ記録)
  - 集団集計は**10名未満のグループを表示しない**(個人特定防止)
  - 年度は4月始まり(`getFiscalYear`)
  - 認証Cookieはセッションスコープ(ブラウザ終了で失効)+20分無操作で自動ログアウト
  - migrationsは番号付きSQLファイルで管理し、ユーザーがSQL Editorで手動実行

## 3. 機能一覧

### 3.1 安全衛生委員会 議事録管理

| 機能 | 内容 | 権限 |
|---|---|---|
| 委員会名の企業別設定 | 企業ごとに委員会名のデフォルト(「衛生委員会」または「安全衛生委員会」)を設定でき、議事録作成時の件名の初期値になる | office / company |
| デフォルト出席者 | 企業ごとにデフォルトの出席者リストを登録でき、新規議事録作成時に自動で入力される(その場で追加・削除可) | office / company |
| 議事録の作成・編集 | 開催日・件名(委員会名+回次等)・出席者・審議事項を構造化して記録。※「産業医が出席した」チェック、「決定事項」「次回開催予定日」「次回予定メモ」の項目は設けない | office / company |
| ファイル添付 | 企業が自社で作成した議事録ファイル(PDF/Word等)や配布資料をアップロードできる(Supabase Storage)。アプリ上で作成する代わりにファイルのみ登録する運用も可 | office / company |
| 共有・閲覧 | 企業内の担当者と産業医事務所で相互閲覧。「従業員に公開」をオンにすると、その企業のemployeeロールがログイン後のマイページの「安全衛生委員会のお知らせ」欄から閲覧できる(公開されるのは公開フラグを付けた議事録・添付のみ) | office / company(自社)/ 公開時はemployee(自社) |
| PDF出力 | 議事録の印刷様式(既存の帳票と同じ print CSS 方式) | 閲覧可能者 |
| 保存年限 | 作成から3年以上(安衛則準拠)。削除は原則不可、officeのみ例外操作(ログ記録) | — |

### 3.2 健康診断結果管理

**注意: 健診結果は法令上、事業者が保有する情報**(ストレスチェックと異なり企業側担当者も取り扱える)。ただし取り扱い者は必要最小限とし、閲覧は全てログに記録する。

| 機能 | 内容 | 権限 |
|---|---|---|
| 健診結果の取込 | CSV一括取込(健診機関の出力形式に合わせたマッピング設定)+個別入力。年度・健診種別(定期/雇入時/特殊)を付与 | office / company |
| 有所見管理 | 検査項目ごとの判定(A〜E等)を記録し、有所見者を自動リストアップ | office / company |
| 就業判定(医師の意見) | 産業医が「通常勤務可 / 就業制限 / 要休業」と意見を記録。意見書のPDF出力 | 判定入力はofficeのみ、閲覧はcompanyも可 |
| 事後措置フォロー | 再検査・受診勧奨の対象者管理、実施状況のステータス管理(未対応/勧奨済/受診済) | office / company |
| 経年比較 | 個人の健診結果の年度推移表示 | office(全企業)/ company(自社)/ employee(本人分のみ) |
| 集計 | 有所見率などの事業場集計(**10名未満のグループは非表示**) | office / company |
| 保存年限 | 健康診断個人票は5年(特殊健診は法令に応じて別途) | — |

### 3.3 ストレスチェック連携(既存データの参照)

新システムからは既存テーブルを**読み取り専用**で参照する。書き込み・スキーマ変更は行わない。

| 機能 | 内容 | 権限 |
|---|---|---|
| 高ストレス者一覧 | 既存`results`から当年度の高ストレス者と面接指導申出状況を表示 | office / jimu(自社・誓約済) |
| 個人統合ビュー | 従業員1人の「健診結果+ストレスチェック結果+面談履歴」を時系列で表示(産業医の判断材料) | officeのみ(companyにはストレスチェック個人結果は**同意分のみ**、既存consented_resultsの原則を踏襲) |
| 集団サマリー | 事業場ごとの高ストレス率・健康リスク(既存の判定図計算モジュールを再利用)と有所見率の並列表示 | office / company(集計値のみ) |

### 3.4 面談管理

| 機能 | 内容 | 権限 |
|---|---|---|
| 面談の種別管理 | 高ストレス面接指導 / 長時間労働面談 / 健診事後措置面談 / 復職面談 / その他相談 | — |
| 予定管理 | 面談予定の登録(日時・対象者・種別・実施方法)。対象者・企業担当者への通知メール(既存Resend基盤を利用、本文に健康情報を書かない原則を踏襲) | office(全企業)/ company(自社の予定の閲覧・日程調整) |
| 実施記録 | 面談実施日・所見・本人への指導内容を記録 | officeのみ |
| 産業医の非公開メモ | 医学的メモ(企業側には**一切表示しない**列として分離) | officeのみ(列単位GRANTで保護) |
| 意見書・報告 | 事業者向けの意見(就業上の措置の要否等)を作成しPDF出力。企業側に公開する内容はこの意見書のみ | 作成はoffice、閲覧はcompany(自社) |
| 既存申出との連携 | 既存`interview_requests`(高ストレス申出)から面談予定をワンクリック作成し、ステータスを同期(既存テーブルの更新は既存の許可範囲内で) | office |

### 3.5 共通・ダッシュボード

- office: 全企業横断ダッシュボード(未対応タスク: 未判定の健診・未実施の面談・申出未対応・次回委員会予定)
- company: 自社ダッシュボード(有所見者フォロー状況・委員会予定・面談予定)
- 通知: メール通知はすべて既存の方針(個人の健康情報を本文に書かない、Resend送信間隔0.6秒+429リトライ)を踏襲
- 監査: 個人情報の閲覧・出力・修正・削除はすべてログに記録(既存`access_logs`を共用するか`hm_access_logs`を新設するかは開発時に決定。ログは削除不可)

## 4. 権限設計

既存の`profiles.role`をそのまま利用する(check制約に`company`が既にあるため**スキーマ変更不要**)。

| ロール | 既存(ストレスチェックWeb) | 新システムでの権限 |
|---|---|---|
| office(産業医事務所) | 全企業の全データ | 全機能・全企業。就業判定・面談記録・非公開メモはofficeのみ |
| company(企業側担当者: 人事・衛生管理者) | 未使用(画面は「利用不可」表示) | **新システムで有効化**。自社の議事録・健診結果・事後措置・面談予定/意見書。ストレスチェック個人結果は同意分のみ(既存原則)。産業医の非公開メモは不可 |
| jimu(実施事務従事者) | ストレスチェック事務(誓約必須) | 従来どおりストレスチェック関連のみ(新システムの健診等にはアクセスさせない。兼務する場合は同一人物にcompanyロールの別アカウント or ロール追加設計を開発時に検討) |
| employee(従業員) | 本人の受検・結果 | 本人の健診結果経年表示・面談予定の確認(範囲は最小限から開始) |

- companyロールの招待は既存`/api/invite`の仕組みを流用(officeが発行)
- 重要操作(健診取込・判定入力・議事録削除・面談記録)は全てSECURITY DEFINER RPC+関数内権限チェック+ログ記録

## 5. 既存システムとのデータ共有方針(最重要)

1. **同一Supabaseプロジェクトに追加する**。既存テーブル・既存RLSポリシー・既存関数は**一切変更しない**
2. 新テーブルは接頭辞 `hm_` を付ける(例: `hm_minutes`, `hm_checkups`, `hm_checkup_items`, `hm_interviews`, `hm_notices`)。`companies`と`profiles`は共用(外部キーで参照のみ)
3. migrationは `0101_` から始める番号体系とし、既存(0001〜0011)と衝突させない。**追加のみ**(create table / create function / create policy)を原則とする
4. ストレスチェックデータ(`results`等)へのアクセスは読み取り専用。companyロールに個人結果を見せる場合は既存の「同意分のみ」原則(consented_results)を必ず経由する
5. ファイル(議事録PDF・健診CSV)はSupabase Storageにバケット `hm-files` を新設し、RLSで企業別にアクセス制御
6. 認証は共通(同じログイン画面設計・同じアカウント)。将来的にヘッダーで両システムを行き来できるリンクを設置
7. リポジトリ・Vercelプロジェクトは新規(例: リポジトリ `kenko-kanri`、URL例 `kenko.mestate.jp` または `kenko-kanri.vercel.app`)。環境変数は既存と同じ値(SupabaseのURL/キー、Resendキー)を新Vercelプロジェクトにも設定
8. **開発中は無料の別Supabaseプロジェクトでスキーマを作り込み、本運用時に`0101_`以降のSQLを本番プロジェクトへ適用**する(試験運用中のストレスチェックWebへの影響ゼロを保証)

## 6. 画面構成案

```
/login                     … 既存と同じ方式(共通アカウント)
/office(ダッシュボード)   … タブ: 予定とタスク / 企業一覧
/office/[companyId]        … 企業別: 議事録 / 健診 / ストレスチェック / 面談 / 設定
/company(企業ダッシュボード)… タブ: 議事録 / 健診結果 / 事後措置 / 面談予定 / お知らせ
/my                        … 従業員: 自分の健診結果(経年)/ 面談予定
/minutes/[id]              … 議事録詳細(印刷・PDF)
/checkup/[userId]          … 健診個人票(経年表示・印刷)
/interview-sheet/[id]      … 面談意見書(印刷・PDF)
```

- UIは既存のデザイン(teal #0F9B8E × orange #E8792B、Meiryo系、カード型、mestateロゴ+フッターCopyright)を踏襲し、両システムで統一感を持たせる
- 帳票はすべて既存方式(print CSS + 「印刷/PDFとして保存」ボタン、印刷時にヘッダー・フッター非表示)

## 7. 非機能要件

- セキュリティ: 既存と同水準(セッションCookie・20分自動ログアウト・列単位GRANT・SECURITY DEFINER RPC・監査ログ削除不可)
- 個人特定防止: 集計表示は10名未満非表示ルールを全集計に適用
- 保存年限: ストレスチェック5年 / 健診個人票5年 / 委員会議事録3年以上。年限内の削除は原則不可
- バックアップ: 本運用前にSupabase Pro(日次バックアップ)へ移行済みであること
- 翻訳機能対応: 既存のDOM保護(DomSafety)と同等の対策を実装
- 規模: 1社平均100名 × 100社 × 5年を想定(既存と同じ)

## 8. 開発の進め方(新セッションへの指示例)

新セッションの最初に、このファイルを添付または貼り付けた上で以下を伝える:

> このリポジトリで、添付の要件定義書に基づき「健康管理Web」を開発してください。稼働中のストレスチェックWeb(別リポジトリ)と同じSupabaseプロジェクトを本番で共用しますが、開発中は無料の別Supabaseプロジェクトを使います。migrationは0101_から、テーブルは hm_ 接頭辞、既存テーブル・ポリシーの変更は禁止です。UIはteal #0F9B8E × orange #E8792B のカード型デザインで、mestateロゴを使用します。

推奨する開発順序(フェーズ分け):

1. **Phase 1**: 基盤(認証・ロール・企業共用)+ 安全衛生委員会議事録(作成・共有・PDF)
2. **Phase 2**: 面談管理(既存の高ストレス申出との連携を含む)
3. **Phase 3**: 健康診断結果(CSV取込・有所見・就業判定・事後措置)
4. **Phase 4**: 統合ビュー・ダッシュボード・集計、companyロールの本格開放

各フェーズごとに、ユーザー(上松先生)がSQL EditorでmigrationをRunし、動作確認してから次へ進む(既存と同じ運用)。
